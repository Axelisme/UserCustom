# Record operations

## Document authority

Classify the fact being changed, not its file. Use this decision before planning or revising work
through either skill, including helper approval steps, shared design, seeds, and corrections.

| Role | Meaning | Change authority |
|---|---|---|
| **User decision** (用戶裁決) | The user's explicit trade-off, constraint, or grant | Preserve until the user supersedes it. |
| **Specification contract** (規格契約) | User-accepted design, outcomes, and acceptance conditions | The Orchestrator may revise details while preserving user decisions and delivery commitments. Changed commitments need a user decision. |
| **Execution plan** (流程規劃) | Slicing, dependencies, order, assignments, execution and verification arrangements | The Orchestrator adjusts these within existing authority and contract obligations without another approval. |

Delivery commitments are agreed outcomes, scope boundaries, public behavior, and acceptance
obligations. Accepted design does not freeze every detail; an explicitly fixed design choice remains
a user decision wherever written. Relabeling a fact cannot lower its authority.
Missing historical scope or authority returns to its owner; new defaults do not replace it.

This classification decides whether the user must decide, not who may execute a change. Existing
mutation grants and role permissions still apply. A receiver returns changes outside its assignment
to the Orchestrator. Record the resulting decision or revision in its owner below.

## Maintain the record

The Orchestrator owns task records except the exact role writes in
[Record permissions](lane-authority.md). Each fact has one owner; other records point to it.

| Fact | Owner |
|---|---|
| Requested outcome and active verbatim Standing orders | INDEX Goal and Standing orders |
| Ticket board | INDEX Tickets, generated by `plan.py locate` |
| Task-level unfinished work and waiting conditions | Tracker Plan, pointing to the owning ticket, question, or decision |
| Specification contract and boundaries | `spec/scope.md`, Status: draft then accepted |
| User answer and its effect; authority and conditions | `decisions/NNNN-slug.md`, cited from the contract |
| Ticket outcome, scope, dependencies, criteria, open user questions | Ticket contract sections |
| Status and branch | Ticket frontmatter |
| Execution milestones | Ticket Plan |
| Collaboration identities, decision grounds, acceptance facts | Ticket Log |
| Review assignment | Dispatch; identity fields in Log under Review rounds below |
| Review judgement | `tickets/<id>/review-NN.verdict.md` |
| Clean-commit gate observations and raw logs | `runs/<short-sha>/` |
| Commits, diffs, execution history | Git and the run |
| Assigned research deliverable, including drafts | `research/`, or `spec/` when freezing a contract; cited by its ticket |
| Proposal awaiting an answer | `spec/`, frozen once proposed |
| Rerunnable task scripts | `scripts/`; output to stdout or `research/` |

Research answers an assigned question with evidence and limitations. Drafts may evolve while the
answer is unsettled; exploratory commands, interim reasoning, and unassigned inventories stay in
the session.

INDEX Goal changes only when the user redefines the outcome. The tracker has no branch, review,
or collection; it stays `doing` until the user completes or abandons the task. Update its Plan when
task-level work or waiting conditions change. Keep answers and ticket states in their owners.

Only the Orchestrator changes status. Frontmatter has `id`, `status`, `depends_on` (a flow list of
this task's IDs, or `[]`), and `branch` when a checkout exists.

| Status | Meaning |
|---|---|
| `todo` | Contract being settled |
| `ready` | Contract, seed, and gates prepared; not started |
| `doing` | Writer dispatched or Orchestrator implementing |
| `review` | Fixed candidate awaiting or undergoing acceptance |
| `blocked` | Started work stopped by a decision, new dependency, or external condition |
| `closed` | All applicable criteria accepted and candidate, if any, collected |
| `dropped` | Abandoned, superseded, or split |

A ready ticket awaiting dependencies stays ready; the board marks `ready ▶` when they are closed.
External conditions belong in the contract with their blocker and owner, not in `depends_on`.

Update status and regenerate the board; status alone needs no Log entry. For a repeated result,
compare identity and content with the saved original. If both match and nothing is new, write
nothing. Differences or uncertain identity require inspection, not deduplication or redispatch.

Log is append-only, newest last, and the final ticket section. Record dispatch identities, review
assignments and verdict pointers, contract changes and their authority, evidence-reuse decisions,
reconcile/collect commits, and unresolved resource ownership. Append necessary events as:
`- MM-DD HH:MM <event>: <fact or source pointer>`, using the current clock.
An ordinary ticket's optional Plan tracks milestones tagged with criterion IDs, not copies of Acceptance.

For a contract revision after ready, preserve superseded wording and its authority in `history.md`,
amend the contract, and log the change. On a ticket size warning, move old Log entries to history;
retain an exact pointer for any identity still needed to verify unfinished work. On an INDEX size
warning, shorten Goal while keeping the orders and board whole.

Put a user question's scenario, impact, options, and recommendation in User decisions. Save the
answer once, verbatim, in the next numbered decision file (select the number from `ls`), first line
`Status: accepted`; cite and log it from the ticket. A decision without a ticket needs only its file.
Mark superseded decisions/proposals `Status: superseded by <file>`. Apply custody to quotations,
ratification, and standing orders. Block only the started work waiting on the answer.

Finish when changed facts are saved in their owners, `locate` shows true ticket status, and tracker
Plan leads to remaining task-level work. Unchanged facts require no record update.

## Review rounds

Rounds use two-digit numbers increasing throughout a ticket's lifetime, including milestone reviews.
Use `../templates/ticket/review.md` as a dispatch template, not a required task artifact.

The complete dispatch names subject commit/tree, baseline, frozen checkout and writer state,
criterion IDs and ticket anchors, gate summaries, repository/skill paths and read conditions,
recovery through the original injected contract, verdict template and absolute output path,
authority, and stop conditions. State explicit none for absent sources. From round 2, include each
previous finding's disposition: fixed with commit, declined with reason, or referred to a user decision.

Log round, child ID, subject commit/tree, baseline, criterion IDs, and absolute verdict path.
The acceptor uses `../templates/ticket/verdict.md`; its verdict identifies subject, baseline,
criteria, evidence, and findings `RNN-F<m>`, with outcome COMPLETED, BLOCKED, or UNREVIEWABLE.
The Orchestrator records the verdict pointer and checks only established criteria. Judgement and
reuse follow Collab's [review operations](../../collab/references/review.md#correct-and-decide);
reuse belongs in Log and never rewrites the verdict's subject.

## Close

Close when a COMPLETED round covers every applicable criterion on the collected candidate,
or when the Orchestrator accepts every gate of a gates-only ticket. Preserve the accepting round
or gate judgement, collected commit, and any retained resource's owner and cleanup condition.
Set closed and refresh the board. Closure is complete when the lane is retired or explicitly retained.

Dropped work keeps unchecked criteria and its reason/replacement pointer in Log. A replacement
may mark an already passed criterion `accepted in <ticket> RNN`. Keep gate evidence in runs and
link to it from verdicts rather than copying it.

## Archive

On the user's completion or abandonment, close or drop every non-tracker ticket, surface unresolved
items, and retire owned temporary resources. Set tracker closed or dropped with the decision source,
run `locate`, then `scripts/plan.py archive`. Archive keeps the record intact, including evidence
and orders; each retained execution resource needs an owner and cleanup condition.
An enduring decision becomes a tracked ADR only on user request.
