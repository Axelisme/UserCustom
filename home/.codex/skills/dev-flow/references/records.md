# Record operations

## Maintain the record

Records live under `.agent_state/plans/<task-id>/` in the main checkout while code worktrees remain
separate. The Orchestrator writes them unless a role's exact write below says otherwise.

Each fact has one **owner record**. Other records link to it.
Research serves an assigned question with conclusions, supporting evidence, and limitations.
Its real deliverable may be drafted and revised while the answer is unsettled. Exploratory commands,
interim reasoning, and unassigned inventories stay in the session.

| Fact | Owner record |
|---|---|
| Goal and verbatim Standing orders | INDEX, written by the Orchestrator |
| Ticket board | INDEX `## Tickets`, generated by `plan.py locate` |
| Task-level unfinished items and waiting conditions | The `tracker` ticket's `## Plan`, with pointers to their owners |
| Approved scope and its boundaries | `spec/scope.md` (`Status: draft`, then `accepted`) |
| A user decision: the answer and its effect | `decisions/NNNN-slug.md`, one per decision |
| Contract, dependencies, acceptance, and open user questions | Ticket contract sections |
| Ticket status and branch | Ticket frontmatter |
| Ticket milestones | Ticket `## Plan` |
| Necessary collaboration events and acceptance decisions | Ticket `## Log`, with identities and source pointers |
| One review round's assignment | Child dispatch, sent by the Orchestrator; round, child ID, subject commit/tree, baseline, criterion IDs, and verdict path in the ticket Log |
| One review round's judgement | `tickets/<id>/review-NN.verdict.md`, written by the acceptor |
| Gate results for a clean commit | `runs/<short-sha>/`, written by whoever ran the gates |
| Commits, diffs, and progress between events | Git |
| Assigned research deliverable, including its draft | `research/`, or `spec/` when it freezes a contract; the ticket cites it |
| A proposal awaiting the user's answer | `spec/`, frozen once proposed |
| Task-owned scripts that can be rerun | `scripts/`; output goes to stdout or a `research/` path |
| Authority and its limits | The decision or grant that confers it, cited from `spec/scope.md` |

The ticket is a GitHub issue: the contract sections are its body, settled before `ready` and rarely
edited after; the Log indexes necessary events and their grounds. The INDEX board is the Kanban view, and
INDEX is the task's README: its Goal is the outcome the user asked for in one or two sentences and
changes only when the user redefines it.

The **tracker** is the task's tracking issue. `create` adds it as `tickets/tracker`; it stays `doing`
until the user completes or abandons the task, has no branch, and is never reviewed or collected.
Its Plan contains task-level unfinished items and waiting conditions, with pointers to the owning
ticket, question, or decision. Update it when that plan or waiting condition changes, not after
each tool action. Keep answers and ticket states in their owners. A task waiting on the user keeps
the tracker `doing`; the Plan points to the question and who must answer it.

**Status** is the Kanban column in ticket frontmatter. Only the Orchestrator changes it.

| Status | Meaning |
|---|---|
| `todo` | The contract is still being settled. |
| `ready` | Contract, seed, and gates are prepared; work has not started. A ready ticket waiting on dependencies stays `ready`; the board shows `ready ▶` once every dependency is `closed`. |
| `doing` | A writer is dispatched, or the Orchestrator is implementing. |
| `review` | A fixed candidate is waiting for, or under, acceptance. |
| `blocked` | Started work is stopped by a user decision, a dependency added mid-flight, or an external condition. |
| `closed` | Every criterion is accepted and the candidate, if any, is collected into integration. |
| `dropped` | Abandoned, superseded, or split. |

Frontmatter holds `id`, `status`, `depends_on` (a flow list of this task's ticket ids, `[]` when
none), and `branch` when a checkout exists. An external condition, such as another task's candidate,
lives in the contract. Set `blocked` when it stops started work and preserve the blocker and its owner.

Update status in frontmatter and regenerate the board. A status change alone needs no Log line.
Only a new collaboration identity, decision ground, or acceptance fact warrants an event. Save the
needed fact in its owner rather than copying progress into other tickets or the tracker.
For a repeated result, compare the identity and content with the saved record. If both match and no
new fact exists, make no new event, including no confirmation-of-no-change entry. A difference or
uncertain identity requires inspection, not an assumed duplicate or a replacement dispatch.

**The Log** is append-only, newest last, and remains the ticket's final section. Write necessary
events as `- MM-DD HH:MM <event>: <fact or source pointer>`.
Record dispatch identities, review assignments and verdict pointers, contract changes and their
authority, evidence-reuse decisions, reconcile or collect commits, and unresolved resource ownership.
These facts cannot be reconstructed from status alone. Git and the run retain finer execution history.
Append with `printf -- "- $(date '+%m-%d %H:%M') <event>\n" >> <ticket.md>` when such a fact changes.

For an ordinary ticket, **Plan** is an optional milestone checklist for work built or reviewed in
parts; tag milestones with their criteria. It does not repeat Acceptance. The tracker uses Plan as
the task-level entry described above.

When authority changes the contract after `ready`, amend the section in place, move the superseded
wording with its authority pointer to the ticket's `history.md`, and add a Log line. When
`size_warnings` names a ticket, move old Log lines to `history.md`. If unfinished work still uses a
moved dispatch or round identity, retain a precise pointer from the current record to that history
entry. Moving the bytes must preserve the lookup needed to verify the live attempt.

A user matter goes in the ticket's User decisions as the question: scenario, impact, options, and
recommendation. The answer is written once, verbatim, to `decisions/NNNN-slug.md` (the next number
from `ls`; first line `Status: accepted`, later `superseded by NNNN`); the ticket links it and logs
one line. A decision that has no ticket needs only its file. A superseded proposal carries
`Status: superseded by <file>` on its first line. A lapsed standing order moves intact from INDEX to
`decisions/NNNN-retire-<slug>.md` with its date and reason, quoting a revocation verbatim. While a
question blocks started work, the ticket is `blocked`; unrelated tickets continue.

When `size_warnings` names INDEX, shorten the Goal; the Standing orders and the board stay whole.

The update is complete when every changed fact sits once in its owner record and the board, after
`locate`, shows each ticket's true status. The tracker Plan points to remaining task-level work.

## Review rounds

A round judges named acceptance criteria of one ticket on one fixed commit. Round numbers are two
digits and continue across the ticket's lifetime, including rounds that cover later milestones.

- The dispatch is the whole bounded assignment. Use `../templates/ticket/review.md` as a message
  template, not a required task file. Include subject commit/tree, baseline, frozen review checkout,
  writer state, criterion IDs with ticket anchors, gate summary paths, applicable instruction/skill
  paths and read conditions, recovery instructions for the original injected contract, verdict
  template and absolute output path, authority, and stop conditions. State explicit none for absent
  sources. From round 2, include each previous finding's disposition: fixed with its commit, declined
  with a reason, or moved to a user decision.
- The ticket Log records round number, child ID, subject commit/tree, baseline, criterion IDs, and
  absolute verdict path so an interrupted parent can locate the live attempt without its old messages.
- `review-NN.verdict.md` is the acceptor's judgement, created from `../templates/ticket/verdict.md`
  at the absolute path the dispatch names. It records the reviewed subject, baseline, criteria,
  evidence references, and findings. Its frontmatter `outcome` is `COMPLETED`, `BLOCKED`, or
  `UNREVIEWABLE`; finding IDs are `RNN-F<m>`.

Subject and contract changes follow Collab's [Subject changes](../../collab/references/review.md#subject-changes).
After the verdict, the Orchestrator checks the boxes it establishes, sets the status, and adds the Log
line; the findings stay in the verdict file. Any coverage reused for a later commit has its own
Orchestrator decision in the ticket Log; it does not change the verdict's reviewed subject.

## Close

A ticket closes when every applicable criterion is checked through a COMPLETED round, or through the
Orchestrator's gate judgement for a gates-only ticket, on the collected candidate. Set
`status: closed`. Preserve the accepting round or gate judgement, collected commit, and any retained
resource owner under [Maintain the record](#maintain-the-record); status alone cannot supply them.
Dropped work keeps its unchecked criteria and a Log line with the reason and any replacement ticket.
A replacement ticket may cite a criterion the original already passed as `accepted in <ticket> RNN`
and check it. Gate logs and summaries stay in `runs/` and archive with the task, like CI logs kept
with a PR; rounds and verdicts point to them rather than copy them.

Closure is complete when the board shows the ticket closed and its lane is retired or has an owner
and cleanup condition in the Log.

## Archive

Archive only when the user completes or abandons the task. First bring every ticket except the tracker
to `closed` or `dropped`, surface anything unresolved, and retire owned temporary resources. Then
set the tracker to `closed` or `dropped` according to that user decision and preserve its source under
[Maintain the record](#maintain-the-record). Run `locate` so the board shows it, then run
`scripts/plan.py archive`. A decision that must outlive
the task becomes a tracked ADR only on user request. Archive is complete when the whole record moved
intact and every retained execution resource has an owner and cleanup condition.
