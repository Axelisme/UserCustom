# Migrate to Orchestrate v137

## From

v136

## Observable changes

v137 replaces the former candidate-oriented command set with one minimum-complete lifecycle.
Task discovery is now `status`; lane readiness and staleness use `lane check` and `lane sync`;
exact integration snapshots use `acceptance start` and `acceptance result`; persistence drift uses
`integration reconcile`; and external waits use `timing pause` and `timing resume`. Passing
acceptance establishes the `accepted` ref, while successful local squash persistence establishes
the `landed` ref. Help and runtime guidance expose only this final grammar.

Package administration is cwd-derived. Doctor comparison is nested under `doctor diff`, release
requires an explicit exact-next version, and the source publishes byte-identical physical Codex
and Pi manifests. The Pi Adapter executable is unchanged. Profile manifests make a one-time
v136-to-v137 schema migration to exactly `{agent_name,prompt_sha256}` for all 31 profiles; later
comparisons track only the extracted name and prompt, excluding runtime/model/configuration
metadata.

## Active-task impact

No automatic conversion, cleanup, acceptance, landing, or abandonment is performed. v136 task
worktrees, refs, branches, reports, pins, and user dirt remain byte-preserved until an operator
chooses a separately authorized action. Because the state model changed, do not continue an active
v136 orchestration run under v137. Finish it with its verified package or explicitly abandon it
under the authority and safeguards that created it; never infer new accepted or landed authority
from old state.

## Manual steps

1. Stop new lane dispatch and read this guide plus the shared admission standard.
2. Verify both logical source packages and confirm their v137 manifests are byte-identical.
3. With current setup authority, run the normal no-argument setup only from the primary source
   checkout. Setup installs the replacement and verifies both logical releases before it removes
   managed retired destinations.
4. Reload the applicable runtime. For Pi, reload the unchanged Adapter binding as required by the
   host runtime.
5. In each repository, inspect `status`, active worktrees, refs, and the existing pin. Decide
   explicitly whether any active pre-v137 task will finish under v136 or be abandoned.
6. After all package and repository checks pass, use separately authorized `pin set` from the
   repository cwd. The pin records adoption; it does not install or select code.

## Verification

Run source and installed `doctor`, then `doctor diff 136 137` unfiltered and once for each runtime
filter. Confirm the current projection is exactly 21 documents, 31 profiles, and one runtime asset;
confirm both manifest files compare equal; confirm historical manifests v130–v136 and migration
guides v131–v136 retain their protected hashes; and confirm the Adapter hash is unchanged.

Run canonical test discovery with zero failures and zero errors before relying on narrower gates.
Then run the v137 release, lifecycle, module, Adapter, setup, lint, type, compile, and shell-syntax
gates. In a disposable repository, exercise create, lane collection, acceptance, local landing,
reporting, and normal removal. Do not use a real HOME for verification.

## Rollback

Stop before the next authority boundary if any verification fails. Before setup, reject the source
and repair it through the normal reviewed lane. After setup, preserve user data and repair forward
to a verified v137 package; do not synthesize v136 state, rewrite a pin, force-delete worktrees, or
invoke abandon as automatic rollback. A failed replacement verification must occur before retired
destination removal. Adapter or runtime failures require a reload or reviewed forward fix, not
unreviewed Git mutation.
