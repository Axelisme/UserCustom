# Migrate to Orchestrate v138

## From

v137

## Observable changes

v138 retires the Pi `orchestrate-pi.ts` Adapter. Pi Root now dispatches admitted lanes through the
native `subagent` surface, and the `orchestrate_pi` tool no longer exists. Root uses the native
`status`, `interrupt`, `resume`, `steer`, and `stop` controls directly; `steer` remains guidance
rather than readiness or terminal evidence. The runtime binding depends on upstream
`pi-subagents` 0.38.0 and its native async lifecycle and `turnBudget` behavior.

The Codex, Claude, and Pi bindings now share the same Git lane contract. `runtime_assets` is
removed from v138 manifests and package projections. Historical v130–v137 manifests retain their
runtime-asset sections so they remain loadable and so `doctor diff 137 138` can report the Adapter
as removed.

## Active-task impact

No automatic conversion, cleanup, acceptance, landing, or abandonment is performed. An active
v137 task must not continue across this release. Finish it with the package and evidence already
verified under v137, or explicitly abandon it under the authority that created it. Do not infer new
acceptance, landing, or cleanup authority from an active v137 task.

## Manual steps

1. Stop new lane dispatch and read this guide together with the shared admission standard.
2. Confirm the v138 source and installed package hashes before changing the installed runtime.
3. With current user authority, manually delete the installed
   `~/.pi/agent/extensions/orchestrate-pi.ts`. It was hard-linked to the repository copy, so both
   names must be removed; setup does not manage a retired runtime asset.
4. Reload Pi and confirm that the `orchestrate_pi` tool is gone.
5. Inspect each repository's task status, active worktrees, refs, and pin. Finish any active v137
   task with its verified package or explicitly abandon it; do not continue it under v138.
6. After package and repository checks pass, use separately authorized `pin set` from the
   repository cwd. The pin records adoption; it does not install or select code.

## Verification

Run source and installed `doctor`; the package projection must be exactly 22 documents, 31
profiles, and 0 runtime assets. Run `doctor diff 137 138` once without a runtime filter and once for
each `codex`, `claude`, and `pi` filter. Confirm every result reports the removed
`.pi/agent/extensions/orchestrate-pi.ts` under `changed_runtime_assets` in the unfiltered and Pi-filtered
results; the Codex and Claude filters must not report that Pi-only asset. Confirm the Codex and Pi
v138 manifests are byte-identical, and that v130–v137 manifests plus v131–v137 migration-guide
hashes are unchanged and still loadable.

Run canonical test discovery with zero failures and zero errors, then the release, lifecycle,
module, setup, lint, type, compile, and shell-syntax gates. Replace the runtime name in each
binding with the same placeholder and confirm the Claude and Codex texts are identical. In a
disposable repository (never a real HOME), exercise create, lane collection, acceptance, local
landing, reporting, and removal. Finally, run one Pi lane through native dispatch, `status`,
`interrupt`, `resume`, and lane-ready; this is the only v138 behavior without existing automated
test coverage.

## Rollback

If any verification fails, stop before the next authority boundary. Before setup, reject the
source and repair it through the normal admitted lane. After setup, repair forward to a verified
v138 package while preserving user data. Do not synthesize v137 state, rewrite a pin, force-delete
worktrees, or use abandon as automatic rollback. The installed Adapter is removed only by the
user's explicit manual step; a runtime failure requires reload or a reviewed forward fix.
