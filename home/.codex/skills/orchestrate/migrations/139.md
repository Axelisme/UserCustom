# Migrate to Orchestrate v139

## From

v138

## Observable changes

v139 moves per-task telemetry inside the managed task root. The append-only event log is now
`.agent_state/worktrees/<task>/telemetry.jsonl` instead of
`.agent_state/orchestrate/telemetry/<task>.jsonl`. Every per-task resource an orchestrate task owns
now lives under one task root together with `integration/`, `acceptance/`, and `lanes/`;
`.agent_state/orchestrate/` retains only cross-task package state such as the version pin.

Telemetry keeps its existing contract. It remains observational rather than authoritative, event
schema and lifecycle operations are unchanged, `record_event` still degrades to a warning while
`timing pause` and `timing resume` still fail loudly, and `status`, `report`, and cleanup expose the
same slots. Task existence is now derived from the task root alone, because telemetry can no longer
survive outside it.

## Active-task impact

No automatic conversion, migration, cleanup, acceptance, landing, or abandonment is performed. A
v138 telemetry file is not moved and not read from its former path. An active v138 task must not
continue across this release: its telemetry would appear empty under v139 and its report would omit
every event recorded under v138. Finish such a task with the package that created it, or explicitly
abandon it under that same authority.

Because v139 no longer removes the former path, any leftover
`.agent_state/orchestrate/telemetry/` directory becomes inert historical data owned by the operator.

## Manual steps

1. Stop new lane dispatch and read this guide together with the shared admission standard.
2. Confirm the v139 source and installed package hashes before changing the installed runtime.
3. In each repository, run `status` and inspect active worktrees, refs, and the pin. Finish or
   explicitly abandon every active v138 task before adopting v139.
4. Once no active task remains, decide explicitly whether to keep or delete any leftover
   `.agent_state/orchestrate/telemetry/` directory. It is historical observation only; nothing
   reads it under v139.
5. After package and repository checks pass, use separately authorized `pin set` from the
   repository cwd. The pin records adoption; it does not install or select code.

## Verification

Run source and installed `doctor`; the package projection must be exactly 23 documents, 31
profiles, and 0 runtime assets. Run `doctor diff 138 139` once without a runtime filter and once for
each `codex`, `claude`, and `pi` filter, and confirm `scripts/_orchestrate/resources.py` is the only
changed script. Confirm the Codex and Pi v139 manifests are byte-identical, and that v130–v138
manifests plus v131–v138 migration-guide hashes are unchanged. Confirm v133–v138 manifests still
load. The v130–v132 manifests predate `runtime_assets` and are already rejected by the v138 and
later structural validator; v139 neither repairs nor worsens that condition, so treat their
byte-level preservation, not their loadability, as the invariant under test.

Run canonical test discovery with zero failures and zero errors, then the release, lifecycle,
module, setup, lint, type, compile, and shell-syntax gates. In a disposable repository (never a real
HOME), exercise create, lane collection, acceptance, local landing, reporting, and removal, and
confirm that telemetry is written to `.agent_state/worktrees/<task>/telemetry.jsonl`, that no file
appears under `.agent_state/orchestrate/telemetry/`, and that removal deletes the telemetry file
before the task root.

## Rollback

If any verification fails, stop before the next authority boundary. Before setup, reject the source
and repair it through the normal admitted lane. After setup, repair forward to a verified v139
package while preserving user data. Do not synthesize v138 state, relocate telemetry files by hand
to make an old task appear continuable, rewrite a pin, force-delete worktrees, or use abandon as
automatic rollback.
