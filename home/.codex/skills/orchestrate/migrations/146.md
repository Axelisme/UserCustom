# Draft: Migrate to Orchestrate v146

This is a source-only migration draft. It does not publish Orchestrate v146, alter the package
version, regenerate a manifest, or authorize setup, pinning, installation, landing, or cleanup.
Apply it only at the separately authorized publication boundary.

## Breaking CLI changes

`lane create` no longer accepts `--group`; callers that supply it receive a structured
`cli_usage` error. An optional `--comment <text>` records a bounded annotation. Use
`lane comment --task-id <task> --lane-id <lane> --text <text>` to overwrite an active lane's
annotation, or `--clear` to remove it. Text is trimmed, single-line, and 1–500 Unicode characters;
empty text never means clear.

`orchestrate.py --version` is the only version query and emits the normal JSON envelope. There is
no `version` subcommand.

## Status projection

Active lanes now appear as `lanes: {"<lane>": {"sha": "<sha>", "comment"?: "<text>"}}`.
Absent and cleared comments are omitted. The managed acceptance-worktree `acceptance` field and
all lane-consumption/group/count/threshold/history projections are removed. The independent
`accepted`, `user_accepted`, `landed`, and real inventory `warnings` fields remain as applicable.

Comments are annotation-only: they do not affect lifecycle, collection, acceptance, landing,
closeability, or cleanup. Comment set/clear events remain append-only telemetry and report history;
comments are projected only while their managed lane is active.

## Active-lane warning

After a successful create, Orchestrate counts currently projected active lanes for the task. Counts
1–8 are quiet. The ninth and every later active create succeeds and returns one factual warning that
names the current count and tells Root to collect/drop unneeded lanes. Collected, dropped, and
historical lanes do not count, and the count is not projected by status or used as a create gate.

## Active-task impact and verification

Existing managed refs, worktrees, acceptance evidence, and telemetry are not migrated automatically.
At the publication boundary, update callers to remove `--group`, read the nested lane objects, and
use the explicit comment command where needed. Verify the source and installed package separately,
then run real-Git CLI tests for version, comment validation/set/clear, terminal history, nested
status, acceptance-field removal, and active counts 1–9. Keep v144/v145 manifests and migrations
byte-for-byte unchanged.

## Dev-flow scaffold

Generated task-record `INDEX.md` files now carry persistent HTML guidance under `Goal`, `Current`,
`Next`, `Envelope`, and `Standing orders`; the comments guide filling without becoming task facts.
The populated `references/example-record/` tree and its dev-flow `SKILL.md` link are removed. No
replacement populated example or template/example divergence validator is added.

## Pi writer guidance

The v146 source guidance keeps `runtime-pi.md` as one file with six sections in operational
order: Dispatch, Writer execution, Recovery, Evidence, Runtime dependency, and Authority. Normal
writer launch and resume omit `turnBudget` without imposing a hard prohibition; an exceptional
budget may hard-cut a child without an approaching-limit warning. Writer launch/resume never uses
`subagent_wait`: interactive mode ends the turn, while goal-active mode reports progress and calls
one `yield_goal` once. Accepted resume uses a five-minute minimum quiet window, while runtime
completion, process-terminal, and needs-attention events remain immediate.

Recovery keeps the four actions same-session resume, same-lane fresh run, re-admit/recut, and lane
drop. A new lane receives a fresh child session even when its ticket/profile is shared. Readiness
requires Pi public `process-terminal.json` proof with state `observed` plus exact Git checks. The
dependency is capability-based, task start runs one `subagent doctor`, and `0.40.0` is recorded
only as the last verified version. No focused runtime reference is added.

## Conditional validation

The v146 lifecycle and dispatch guidance now carry the admission-recorded `Validation mode: TDD`
or `Validation mode: direct — <specific reason>`. A reasonable production red oracle requires TDD, with
Contract tests, focused red evidence, and normalized `Immutable:` declarations before implementation.
When no reasonable production red state exists, the frozen Contract's acceptance surface is
validated directly without fabricated tests, red evidence, or `Immutable:` ceremony. File type
never selects the mode; workers cannot downgrade TDD, and a changed mode judgment returns to Root
for re-admission. Direct-mode handoffs report the frozen Contract pointer, changed/protected paths,
direct validation results, and the exact clean SHA. This draft adds no CLI flag, status field, or
second state store.
